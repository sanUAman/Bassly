# ADR-0003: API Style and Error Model

## Status
Accepted

## Date
2025-12-16

## Context

Проєкт *Bassly* — це вебсервіс для бронювання квитків на музичні концерти,
реалізований як **модульний моноліт** на Django (Django ORM без DRF).

API використовується:
- для взаємодії з frontend-клієнтом;
- для виконання CRUD-операцій над доменними сутностями (Events, Tickets, Orders);
- як контракт, зафіксований у OpenAPI (Swagger).

Команда проєкту складається з одного розробника.
Потрібно було обрати стиль API, формат помилок та політику HTTP-кодів,
які є зрозумілими, стандартними та легко розширюваними.

---

## Decision

### 1. Стиль API

Обрано **REST-style API** з такими принципами:

- ресурсоорієнтований дизайн (`/events`, `/tickets`, `/orders`);
- використання HTTP-методів за призначенням:
  - `GET` — читання;
  - `POST` — створення;
  - `PUT/PATCH` — оновлення;
  - `DELETE` — видалення;
- JSON як єдиний формат обміну даними;
- відсутність логіки бізнес-рівня в API-шарі (вся логіка в `service/`).

---

### 2. Політика HTTP-кодів

API повертає **стандартні HTTP-коди**, що відповідають REST-практикам:

| Код | Значення | Коли використовується |
|----|--------|----------------------|
| 200 OK | Успішна операція | GET, PUT |
| 201 Created | Ресурс створено | POST |
| 400 Bad Request | Помилка валідації | некоректні або відсутні поля |
| 404 Not Found | Ресурс не знайдено | неіснуючий ID |
| 409 Conflict | Конфлікт стану | бізнес-обмеження |
| 500 Internal Server Error | Внутрішня помилка | неочікувана помилка сервера |

---

### 3. Формат помилок

Всі помилки API мають **єдиний JSON-формат**:

```json
{
  "error": "Human-readable error message"
}

Принципи:
- без HTML-відповідей;
- без stack trace у відповіді;
- повідомлення орієнтовані на клієнта API;
- деталізація логів — лише на сервері;

---

### 4. Валідація даних

- вхідні дані перевіряються на рівні service/;
- API-шар відповідає лише за:
 - прийом запиту;
 - виклик use-case;
 - повернення відповіді;
- при помилці валідації повертається 400 Bad Request.

---

### 5. Відповідність OpenAPI

API повністю відповідає OpenAPI-специфікації:
- всі ендпоїнти описані в openapi.yaml;
- відповіді (body, status codes) строго відповідають схемам;
- API-контракт є джерелом істини (contract-first approach);
- Swagger Editor використовується для валідації контракту;

## Alternatives Considered

### 1. RPC / Action-based API

Відхилено через:
- відсутність стандартних HTTP-семантик;
- гіршу читабельність контракту;
- складнішу інтеграцію з OpenAPI.

---

### 2. GraphQL

Відхилено через:
- надлишкову складність для навчального проєкту;
- відсутність потреби у складних запитах;
- вищий поріг входу.

---

## Consequences

### Позитивні
- зрозумілий і стандартний API;
- легка інтеграція з frontend;
- простота тестування;
- чіткий контракт через OpenAPI;
- відповідність industry best practices;

### Негативні
- менш гнучкий, ніж GraphQL;
- необхідність підтримувати OpenAPI-специфікацію вручну.
