# ADR 0001 — Вибір архітектурного стилю (Моноліт чи Мікросервіси)

**Дата:** 2025-12-11  
**Статус:** Прийнято

---

## 1. Контекст

Проєкт — вебсервіс для бронювання та продажу квитків на музичні концерти.  
Основні функціональні області:

- Events (концерти)
- Ticketing (квитки, бронювання)
- Orders & Payments (замовлення, оплата)
- Auth (користувачі, ролі)
- Notifications (майбутній модуль)
- Analytics (майбутній модуль)

Стан проєкту:
- Рання стадія розробки (мінімум компонентів).
- Архітектура ще формується.
- Відсутня необхідність у масштабуванні по сервісах.
- Невелика кодова база, незначне навантаження.

Процес розробки:
- Команда складається з **1 розробника**.
- Весь функціонал створюється послідовно.
- Вимоги до швидкого оновлення та простоти підтримки переважають над вимогами до масштабування.

---

## 2. Рішення

**Обрано монолітну архітектуру на етапі пілоту.**

### Чому моноліт:

- Простота розробки: один репозиторій, одна кодова база.
- Швидкість реалізації: не потрібно налаштовувати окремі сервіси, мережеві взаємодії, брокерів, інфраструктуру.
- Простіше тестування та дебаг.
- Легше змінювати структуру домену — DDD ще в процесі формування.
- Для команди з 1 людини — оптимальний варіант.

Моноліт дозволяє:

- організувати чіткі bounded contexts всередині одного проєкту,
- надалі безболісно виділити окремі модулі в мікросервіси, якщо буде потреба.

---

## 3. Альтернативи

### **Альтернатива 1: Мікросервіси з самого початку**

#### Плюси:
- Можна окремо масштабувати Ticketing або Payments.
- Краща ізоляція компонентів.
- Підходить для великих команд.

#### Мінуси:
- Значна інфраструктурна складність: API gateway, message broker, CI/CD для кожного сервісу.
- Високі витрати на підтримку.
- Надмірно складно для прототипу й одного розробника.
- Ускладнює внесення змін у домен, який ще формується.

### **Альтернатива 2: Модульний моноліт (modular monolith)**

#### Плюси:
- Краща структуризація.
- Можна пізніше легко виділити сервіс.

#### Мінуси:
- Вимагає додаткової модульної дисципліни.
- Все одно складніше, ніж простий моноліт.

---

## 4. Наслідки

### Позитивні
- Простота деплойменту — один застосунок, одна база.
- Мінімальні витрати часу на інфраструктуру.
- Вся логіка доступна в одному процесі — немає мережевих затримок.
- Простіше впроваджувати зміни на ранньому етапі, коли домен активно уточнюється.
- Швидке розгортання середовищ (локальне та продакшн однакові).

### Негативні
- Менше гнучкості у масштабуванні (коли користувачів стане дуже багато).
- У майбутньому можливе ускладнення коду, якщо не дотримуватися модульності.
- Перехід на мікросервіси вимагатиме рефакторингу, але він можливий після стабілізації домену.

---

## 5. Висновок

На даному етапі проєкту, з урахуванням обмежених ресурсів та невеликої команди, **моноліт — найбільш раціональне рішення**.  
Дає можливість:
- швидко розвивати функціонал,
- чітко формувати bounded contexts,
- за потреби — у майбутньому виділити модулі в окремі мікросервіси.
